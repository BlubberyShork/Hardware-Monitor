# System Info — Distributed Hardware Telemetry Platform

> **This project is not designed for plug-and-play builds.** It includes a custom KMDF kernel-mode driver that requires the Windows Driver Kit, test-signing enabled on the target machine, and manual driver deployment. The user-space telemetry platform depends on NVIDIA NVAPI, AMD ADL2/ADLX, open62541pp, and a PKI certificate chain generated by the included scripts. If you are here to evaluate the code rather than run it, see the [Demo](#demo) section below.

---

## Overview

A distributed hardware monitoring and telemetry system for Windows. The platform collects live CPU and GPU metrics from one or more machines and streams them over OPC UA to a centralized control center for real-time visualization.

### Architecture

- **Kernel-mode driver** (`drivers/`) — Written in C using the Kernel-Mode Driver Framework (KMDF). Reads hardware-level data (per-core temperature) that standard user-space APIs cannot access. Communicates with user-space via IOCTLs. Supports AMD Zen and Intel Core (DTS-capable) processors. Utilization, Power, and Clock speed retrieval are next on the roadmap.
- **User-space backend** (`System_Info/`) — C++20 application. Queries GPU metrics via NVIDIA NVAPI and AMD ADL2/ADLX, CPU/motherboard/storage data via WMI/WBEM, and driver data via IOCTLs. Publishes all telemetry to the OPC UA server.
- **OPC UA server** (`OPC_UA/`) — Secure OPC UA server (open62541pp with mbedTLS encryption) that acts as the telemetry bus between backends and frontends.
- **Control center** (`control_center/`) — Frontend that subscribes to the OPC UA server and renders a live hardware dashboard.
- **PKI infrastructure** (`scripts/gen_pki.py`) — Local certificate authority and per-device certificate generation for OPC UA mutual TLS.

### Hardware tested

This project has only been tested on the hardware I personally have access to: two CPUs (AMD Zen, Intel Core) and two GPUs (NVIDIA, AMD). I do not currently have a machine powerful enough to run Windows inside a VM for isolated driver testing.

## Prerequisites

### Required for all components

- Windows 10/11
- [Visual Studio 2022](https://visualstudio.microsoft.com/) with the **Desktop development with C++** workload (MSVC compiler + Ninja)
- [CMake](https://cmake.org/) 3.20+
- [Python](https://www.python.org/) 3.11+ (build scripts use `tomllib`)
- [OpenSSL](https://www.openssl.org/) (for PKI certificate generation)
- [mbedTLS](https://tls.mbed.org/) (OPC UA encryption)

### Required for the backend (`System_Info/`)

- [vcpkg](https://vcpkg.io/) (dependency manager)
- [NVIDIA NVAPI](https://developer.nvidia.com/rtx/path-tracing/nvapi/get-started) (GPU telemetry — NVIDIA cards)
- [AMD ADL2 / ADLX SDKs](https://gpuopen.com/adl/) (GPU telemetry — AMD cards)

### Required only for the kernel-mode driver (`drivers/`)

> **Important:** The driver is entirely optional. The rest of the platform functions without it. **Do not attempt to build or deploy the driver** unless you have a dedicated test machine or VM with test-signing enabled. Building the driver will fail without the WDK, and deploying an unsigned driver on a machine with Secure Boot and without test-signing mode will not load. 

- [Windows Driver Kit (WDK)](https://learn.microsoft.com/en-us/windows-hardware/drivers/download-the-wdk)
- Test-signing enabled on the target machine:
  ```cmd
  bcdedit /set testsigning on
  ```

## Configuration

All SDK and tool paths used by the build scripts are centralized in `build_config.toml` at the project root. A tracked example is provided:

```
cp build_config.toml.example build_config.toml
```

Edit `build_config.toml` to match your machine's install locations for MSVC, vcpkg, mbedTLS, WDK, and OpenSSL.
mbedTLS will (likely) soon be included as a submodule in third_party/

### Environment variables

The following must be set at runtime (not in the config file):

| Variable | Description |
|----------|-------------|
| `SERVER_IP` | IP address of the OPC UA server host. Used by the server, backend, and control center to form the endpoint URL (`opc.tcp://<SERVER_IP>:4840`). |

## Building & Running

All build scripts live in `scripts/` and **must be run from the project root**.

### Build order

The components have the following dependency chain:

```
1. scripts/gen_pki.py               (one-time: generate CA + device certificates)
2. scripts/opcua_build.py           (build the OPC UA server)
3. scripts/build_drivers.py         (optional: build + sign the kernel driver)
4. scripts/build.py                 (build the user-space backend)
5. scripts/build_control_center.py  (build the control center frontend)
```

Steps 3 and 4 have no ordering dependency on each other, but `build_drivers.py` must complete before `build.py` if you want the driver integrated. Steps 4's two scripts (`build.py` and `build_control_center.py`) are independent of each other.

### Step-by-step

**1. Generate PKI certificates (one-time)**

```bash
python scripts/gen_pki.py init-ca
python scripts/gen_pki.py add-device server --uri urn:myorg:telemetry:server --dns localhost --ip 127.0.0.1
python scripts/gen_pki.py add-device control-center --uri urn:myorg:telemetry:control-center --dns localhost
```

**2. Build the OPC UA server**

```bash
python scripts/opcua_build.py -b
```

**3. (Optional) Build and deploy the driver**

Requires admin privileges, WDK, and test-signing enabled.

```bash
python scripts/build_drivers.py -b     # build only
python scripts/build_drivers.py -bd    # build and deploy
```

**4. Build the backend and/or control center**

```bash
python scripts/build.py -b                    # backend
python scripts/build_control_center.py -b     # control center
```

### Running

Set the `SERVER_IP` environment variable, then start components in order:

```bash
# Start the OPC UA server
python scripts/opcua_build.py -r

# Start the backend (separate terminal)
python scripts/build.py -r

# Start the control center (separate terminal)
python scripts/build_control_center.py -r
```

### Multi-machine deployment

The build scripts are intentionally kept separate because, in practice, they run on different machines. For example: the desktop acts as the OPC UA server, runs its own backend, hosts the CA, and runs the control center. A laptop only runs `build.py` (and optionally `build_drivers.py`) to contribute its telemetry to the server.

### Clean builds

```bash
python scripts/clean.py          # removes System_Info/build/
python scripts/opcua_clean.py    # removes OPC_UA/build/
```

## Project Structure

```
System_Info/
├── scripts/                  # Build, clean, and PKI scripts
├── System_Info/              # User-space backend (C++20)
├── OPC_UA/                   # OPC UA server
├── control_center/           # Frontend dashboard
├── drivers/                  # Kernel-mode driver (KMDF/C)
├── user_space_common/        # Headers shared across user-space components
├── kernel_common/            # Headers shared between driver and driver client
├── third_party/              # Vendored SDKs (NVAPI, ADL, ADLX, open62541pp)
├── pki/                      # Generated certificates (gitignored)
├── build_config.toml         # Local SDK paths (gitignored, see .example)
├── build_config.toml.example # Template for build_config.toml
└── vcpkg.json                # vcpkg manifest
```
